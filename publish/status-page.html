After the first install, use the launcher

Once the mod is installed, start the game through the Night City Online launcher from then on. It handles four things you would otherwise get wrong:

  • Signs you in with Discord, and checks you are a member of the server.
  • Keeps your game files current, and refuses to launch if they are out of date.
  • Passes the right launch flags automatically — the most common reason this mod silently does nothing is a mistyped launch option.
  • Shows whether the server is up and how many people are on it.

Windows will warn that it is unsigned the first time — More info → Run anyway. That is expected for an app without a paid code-signing certificate.

There is also a PlayNightCityOnline.bat on the release as a fallback for anyone who would rather not run a launcher. It updates and launches, and nothing else.

Installing it the first time

Full instructions ship inside the zip as INSTALL.txt. The short version:

  1. Back up bin\x64, engine, r6 and red4ext from your game folder. Your saves are not touched, but a way back is worth two minutes.
  2. Only if you have Cyber Engine Tweaks: disable it. Rename bin\x64\version.dll to version.dll.off. CET running alongside this mod has caused a full GPU hard-lock needing a power cycle. If that file does not exist, you do not have CET — skip this step. Most people do not have it unless they installed it deliberately. Other signs of it: a bin\x64\plugins\cyber_engine_tweaks\ folder, or ~ opening a console overlay in game.
  3. Install all six prerequisites from the prerequisites folder, in the order listed in INSTALL.txt. Extract each into your Cyberpunk 2077 folder. These exact versions are the ones verified on 2.31 — mixing versions is the most common reason it won't start.
  4. Copy the mod folder into red4ext\plugins\ and rename it to zzzCyberpunkMP. The zzz makes it load after the libraries it depends on.
  5. Add launch options in Steam, GOG or Epic: 
    --online --ip=SERVER_ADDRESS --port=11778
    The = signs are not optional. Writing --ip 1.2.3.4 with a space silently fails — you connect to localhost and time out with no error anywhere explaining why. Without --online the mod stays dormant and your game runs exactly as normal, which is a useful way to check nothing broke.
Linux and Steam Deck

Untested — but there is no known reason it should not work. Cyberpunk runs through Proton, which is a Windows environment, so the mod does not need a Linux build; it needs to load inside the Proton prefix. Everything it is built on — RED4ext, redscript, Codeware, TweakXL — is commonly used under Proton already.

The install steps translate directly: same prerequisites, same folder layout, same launch options. If you try it, tell us how it goes either way — you would be the first, and "it worked" is worth as much as a bug report.

Hosting a server on Linux is properly supported, not just tolerated: the server builds natively on Linux in CI, and the repository ships a Docker Compose setup for it.

Connecting to each other

The server listens on UDP 11778. Tailscale is the easiest route with no port forwarding. If nobody can reach your server, check the firewall first: Windows auto-creates rules scoped to the Public profile, but Tailscale registers as Private, so traffic is dropped silently. Also note that ping failing proves nothing — Windows blocks inbound ICMP by default.

The blocker: remote spawn crash

When a second player joins, one client dies. No RED4ext crash report, no exception dialog — a raw access violation. It has flipped between machines, so it is not hardware- or install-specific.

Solved — 12 August

A movement update arriving before the puppet was ready. When a remote player spawns, the client creates the puppet and then finishes registering it a fraction of a second later. A real player is transmitting movement the entire time, so their first update reliably landed inside that gap — and the code handling it assumed the registration had already happened. It hadn't, so it read from nothing and the game died.

The fix does two things: refuse to act on an update for a puppet that isn't ready, and register it up front so early movement is stored rather than thrown away. Guarding alone would have discarded the first fraction of a second of someone's movement and made them snap into place on arrival.

Why it took so long: the test tool built to reproduce it spawned a fake player — and fake players never move. It could never have triggered the bug. Meanwhile every real player carried both movement and appearance data, so the appearance data looked like the culprit for days. It was a coincidence.

Still needs confirming in a real two-player session before it can be called done.

How it was found

The client is now instrumented with 21 numbered checkpoints across the whole spawn path. A single session captured a surviving puppet and a crashing one side by side, which is what made this readable: 

puppet that lived   PROBE 1..10   spawn
                    PROBE 21      appearance callback   (+41ms)
                    PROBE 17..20  animation attach      (+43ms)
                    PROBE 11..16  promotion poll        (+184ms)

puppet that died    PROBE 1..10   spawn
                    <log ends>                          (+40ms)

Identical code, identical puppet type, opposite outcomes. The crash lands in the window where the game asynchronously assembles the entity — before any mod code touches it again. That is why the checkpoints simply stop: there is nothing of ours left running in there to report.

The logging sink flushes on every message, so a log that stops is a real execution boundary, not a lost buffer.

Already ruled out — please don't re-suggest these

Each was tested with an instrumented build. Every one cost a two-machine session to disprove. If you want to revive one, bring new measurement.

Cyberpunk's main menu is itself a world, so the hook fired 0.4s after startup and connected before any save existed. The server then streamed players into a world with no game in it. What is left

Everything the mod does during a spawn has now been measured and cleared. What remains is the game's own asynchronous entity construction — the roughly 40 ms between our Spawn() returning and the engine's entity attached callback firing. No mod code runs in that window, which is exactly why adding more checkpoints has stopped being useful.

  • Puppet mesh construction is the strongest remaining candidate. Remote players are built on the game's MaMuppet / WaMuppet character records — the bodies the character creator uses. Whether those still assemble correctly on 2.31 is unverified.
  • Placement is not yet separated from timing. Puppets that arrive far away survive; puppets that arrive next to you do not. Neither has ever actually been seen in-world, so it is still open whether the trigger is the game streaming the puppet in, or something about mid-session spawns generally.

Solo reproduction now works

A debug command spawns a fake remote player, so the crash can be reproduced without a second person. It was silently broken until 12 August — the spawn broadcast deliberately skips the entity's owner, and the fake player was owned by whoever summoned it, so the one client that needed the message was the only one excluded from it.

How to help

If you're testing

The single most valuable thing right now is a crash log with probe numbers in it.

  1. Disable Cyber Engine Tweaks. It hard-locks the machine alongside this mod.
  2. Launch with the = form. The space-separated form silently does nothing and you will connect to localhost instead: 
    --online --ip=<server> --port=11778
  3. Spawn into the world, then reproduce. With a second player, just have them join. Solo, type /dummy in chat to fabricate a fake remote player that drives the same code path.
  4. Grab the log. The mod writes one timestamped file per launch into a logs\ folder next to the mod DLL, so crashes no longer overwrite each other. Ignore the file size Explorer shows — Windows reports a stale size while the game holds the file open, so a full log can look empty.
  5. Post the whole file. Not a screenshot, not the last few lines — the ordering across the whole log is what we read.

If you're coding

Two traps have each burned a full day. Please read these before building.

  • Upstream main does not build from a clean clone. Its unpinned dependencies now resolve too new. CI passes only because it restores a cached package set. You need protobuf-cpp 29.3 and Windows SDK 10.0.22621.0; SDK 10.0.26100 breaks the build.
  • Building is not deploying. The install step needs its output prefix spelled out, or it prints install ok! while writing somewhere the game never reads — and you test yesterday's binary: 
xmake build -j 4 Client
xmake install -o distrib Client

Always confirm the timestamp on the deployed DLL actually moved.

Ground rule

Please don't propose a fix for the spawn crash until a probe log exists. Six theories have already been burned by reasoning ahead of measurement, and each one cost a real test session. Once we have the probe number, the fix will be obvious — and it will be correct.

Roadmap

Ordered by dependency, not ambition. Each stage unblocks the next, and nothing below stage one is worth starting until the crash is closed — an unstable session makes every other bug unreproducible.

Stage 1 Blocking

A session that doesn't crash

  • Identify the failing statement from a probe log, and fix it.
  • Strip the temporary probes once the cause is known.
  • Confirm two players can stay connected for a sustained session.
Stage 2 Next

Players who look and move right

  • Equipment sync — replace the debug helper that returns empty item names on 2.31.
  • Movement speed — currently arrives as garbage, suspect a struct offset moved.
  • Interpolation quality, once speed is trustworthy.
  • Restore the / chat hotkey, which a 2.2-era interface override broke.
Stage 3 In progress

Joining a server from the main menu

You used to launch with command-line flags, load a singleplayer save, then open a server browser attached to the in-game HUD. The first two steps are gone.

  • A Multiplayer entry on the title screen — done, 13 Aug. It sits alongside Continue and Load Game, and opens the game's own Load Game screen rather than a copy of it. Pick a save and you arrive connected. The decision is carried across the save load by the network system, which is the one object that survives a world change — script state does not.
  • A character chooser, so your multiplayer identity stops being whatever singleplayer save you happened to load. This is the largest piece here: it needs server-side persistence to be real, so it lands alongside Server durability below.
  • A proper launcher — done. Night City Online is a real Windows application: Discord sign-in, membership check, mod install and update, file verification, server status and player count, patch notes, and a self-update check. It refuses to launch when your files are out of date, because a mismatched client is the fastest way to produce a confusing crash.
  • An in-game Start Server button — deliberately not planned. Supervising an external server process from inside the game means handling crashes, port conflicts, and orphaned processes on exit. A desktop shortcut does the same job with none of that.
Stage 4 Designed

Gameplay primitives

Both borrowed from CyberMP, which solved these already. Designs exist; neither is built.

  • Event veto. A way for server logic to cancel a game event before it happens — starting with combat, so damage is authoritative rather than whatever each client decided locally.
  • Typed RPC router. Today every new network message means editing the protocol definition and regenerating bindings. A dispatch layer over the existing generic call would let gamemode authors add events without touching the build.
Stage 5 Researched

Server durability

Patterns taken from SkyMP, a mature Skyrim multiplayer project with years of production use. Worth copying rather than rediscovering.

  • Movement validation with snap-back, so a client cannot teleport itself.
  • Interest management — only send a player what is near them, instead of everything.
  • Persistence, so a server remembers players between restarts.
  • A transport abstraction with a mock, so networking logic becomes testable without two machines and a copy of the game.
Ongoing Active

Getting fixes upstream

The 2.31 compatibility fix and the build repairs are not project-specific — they help anyone trying to run this mod today. Several pull requests are open against the upstream repository.

Known cosmetic issues

  • Remote players have no gear. Item names are built with a debug helper that returns empty strings on 2.31, so equipment serialises blank and every remote spawn logs eight failed item creations. Harmless, well understood, low priority until the crash is fixed.
  • The / chat hotkey doesn't open the HUD. The mod ships an archive overriding a 2.2-era interface file, which is what registers the key listener. There is a debug menu bar as a workaround.

Everything above is either measured or explicitly marked unverified. Where something is a guess, it says so. If you find a claim here that contradicts what you observe, that is worth raising — several entries on this page exist because an earlier confident conclusion turned out to be wrong.
